# Contributing

The README describes the product. This describes working on it.

This repository is the collector and the engine. The hosted control plane, the dashboard and the
public site are not here; nothing in this repository depends on them, and that is deliberate.

## What you need

- Node 22 or newer, and pnpm (the version in `packageManager` — `corepack enable` will pick it up)

That is all. Nothing here needs a database, a container or an account.

## First run

```sh
pnpm install
pnpm audit:check          # runs the collector against whatever MCP config you have
```

To work against the fixtures rather than your own servers:

```sh
pnpm --filter nulladrift test
```

## Tests

`pnpm -r test` runs every suite, and all of it runs offline. The fixture servers in
`packages/cli/test/fixtures/servers/` are real MCP servers started as subprocesses, which is why
the drift tests exercise the wire rather than a mocked client.

`examples/mcp.lock` is generated by the real builder and checked in CI. If you change what lands
in the lock, regenerate it:

```sh
pnpm example:emit
```

## The two packages

| Package | What it is |
| --- | --- |
| `packages/cli` | the `nulladrift` binary. Bundles the engine with tsup, so it ships with no workspace references. |
| `packages/core` | the lockfile model, canonicalization and the diff engine. Published as `@nulladrift/core`. |

**`@nulladrift/core` is a devDependency of the CLI on purpose.** tsup bundles it; a regular
dependency would put a `workspace:*` reference in the published tarball that npm cannot resolve.

**Its `exports` point at source and `publishConfig.exports` points at `dist`.** The workspace
resolves TypeScript directly, so nothing has to be built before anything else can typecheck, while
the published artifact is compiled JavaScript with types. The control plane consumes that
published artifact rather than a copy of this source, because both sides have to reach the same
answer and that means one implementation, not two.

## Conventions worth knowing

These are the ones that have bitten someone already.

**A test must not re-implement what it tests.** Import the subject. If importing it is awkward
because of a module-level dependency, that is usually a reason to move the subject, not a reason
to copy it.

**Fixtures come from the product.** A fixture the product would never have produced tests a world
that cannot occur.

**Comments say why, not what.** The code is readable; the reasoning behind a decision usually is
not. The useful comment is the one that stops the next person undoing something deliberate.

**No em dashes in anything a user reads.**

## Before you push

```sh
pnpm -r typecheck && pnpm -r lint && pnpm -r test && pnpm -r build
```

That is what CI runs, in that order, plus a check that `examples/mcp.lock` still matches what the
product writes.

## Where decisions are written down

- `docs/lockfile.md` — the lockfile format and why it is digested the way it is
- `docs/comparison.md` — what else exists, measured, and how this differs

Changing what counts as a change is a contract, not a refactor: `CHANGE_KINDS` in
`packages/core/src/changes.ts` is shared with the control plane and with any SARIF consumer, so
renaming one is a major version.
