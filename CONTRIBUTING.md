# Contributing

The README describes the product. This describes working on it.

This repository is the collector and the engine. The hosted control plane, the dashboard and the
public site are not here; nothing in this repository depends on them, and that is deliberate.

## What you need

- Node 22 or newer, and pnpm (the version in `packageManager` — `corepack enable` will pick it up)

That is all. Nothing here needs a database, a container or an account.

## First run

```sh
pnpm install
pnpm audit:check          # runs the collector against whatever MCP config you have
```

To work against the fixtures rather than your own servers:

```sh
pnpm --filter nulladrift test
```

## Tests

`pnpm -r test` runs every suite, and all of it runs offline. The fixture servers in
`packages/cli/test/fixtures/servers/` are real MCP servers started as subprocesses, which is why
the drift tests exercise the wire rather than a mocked client.

`examples/mcp.lock` is generated by the real builder and checked in CI. If you change what lands
in the lock, regenerate it:

```sh
pnpm example:emit
```

## The two packages

| Package | What it is |
| --- | --- |
| `packages/cli` | the `nulladrift` binary. Bundles the engine with tsup, so it ships with no workspace references. |
| `packages/core` | the lockfile model, canonicalization and the diff engine. Published as `@nulladrift/core`. |

**`@nulladrift/core` is a devDependency of the CLI on purpose.** tsup bundles it; a regular
dependency would put a `workspace:*` reference in the published tarball that npm cannot resolve.

**Its `exports` point at source and `publishConfig.exports` points at `dist`.** The workspace
resolves TypeScript directly, so nothing has to be built before anything else can typecheck, while
the published artifact is compiled JavaScript with types. The control plane consumes that
published artifact rather than a copy of this source, because both sides have to reach the same
answer and that means one implementation, not two.

## Conventions worth knowing

These are the ones that have bitten someone already.

**A test must not re-implement what it tests.** Import the subject. If importing it is awkward
because of a module-level dependency, that is usually a reason to move the subject, not a reason
to copy it.

**Fixtures come from the product.** A fixture the product would never have produced tests a world
that cannot occur.

**Comments say why, not what.** The code is readable; the reasoning behind a decision usually is
not. The useful comment is the one that stops the next person undoing something deliberate.

**No em dashes in anything a user reads.**

## Branches

`develop` is the default branch and the one pull requests target. `main` holds the last release
and nothing else: it changes only when `develop` is merged into it, and every `v*` tag lives
there. So `main` always answers "what is published" without anybody having to check.

```
feature ──PR──▶ develop ──merge──▶ main ──tag v0.1.6──▶ npm
```

Both branches require their pull request to pass CI, and neither accepts a direct push or a
force push. There is no required reviewer, so a maintainer can merge their own work; the gate is
the check, not a second person.

Releasing is: open a pull request from `develop` to `main`, merge it, then tag `main`. The tag is
what publishes, and the workflow refuses a tag that disagrees with either package's version.

## Releases are weekly, and you do not bump the version

**Do not touch `package.json` versions or `src/lib/version.ts` in a feature branch.** Write what
changed under `## [Unreleased]` in `CHANGELOG.md` and stop there.

On Thursday the `release-pr` workflow reads those notes, works out whether they amount to a minor
or a patch, writes the bump and the dated changelog entry onto a `release/x.y.z` branch, and opens
a pull request. A week with nothing under `## [Unreleased]` opens nothing.

This exists because the version used to be bumped in whichever branch happened to be open, and
twelve versions reached the registry in fourteen hours. Two of them were ten minutes apart, for
work that was one change; nobody could have installed the first, and npm never lets a version
number be reused. The author of one change cannot see what else is going out beside it, which is
the thing a version number is supposed to describe.

Nothing past the pull request is automatic. Merging it is a person reading what is about to be
published, which is the whole point of batching -- an auto-merge would hand back exactly what the
cadence was meant to buy.

**A fix that disables or bypasses a control does not wait for Thursday.** Run `release-pr` by
hand, or cut the release the usual way. A week is the wrong answer for something an attacker can
switch off; it is the right answer for everything else.

It follows that this repository's own `minimumReleaseAge` policy and its practice now agree. A
tool whose subject is dependency drift should not be installing packages nobody has looked at,
including its own.

## Sign off every commit

Contributions come in under the [Developer Certificate of Origin](https://developercertificate.org)
(DCO) 1.1. Signing off a commit certifies that you wrote it, or otherwise have the right to
submit it under this repository's MIT licence, and that you understand the contribution and your
sign-off are kept in the public history.

```sh
git commit -s
```

That adds a line with the name and email from your git config:

```
Signed-off-by: Your Name <you@example.com>
```

Every commit you contribute needs one, merge commits included, and CI checks it: a pull request
from a fork fails the `check` job until every commit carries a sign-off naming its own author. To
sign off the commits already on a branch, `git rebase --signoff develop` and push it again; merge
with `git merge --signoff`. Branches pushed to this repository itself, by the maintainers and the
release app, are not checked.

**A DCO, not a CLA.** You keep the copyright in what you write and license it under MIT like the
rest of the code; nobody is asked to assign anything. It also means the licence cannot be changed
later without every contributor agreeing, which is the point: what you contribute stays MIT.

## Before you push

```sh
pnpm -r typecheck && pnpm -r lint && pnpm -r test && pnpm -r build
```

That is what CI runs, in that order, plus a check that `examples/mcp.lock` still matches what the
product writes.

## Where decisions are written down

- `docs/lockfile.md` — the lockfile format and why it is digested the way it is
- `docs/comparison.md` — what else exists, measured, and how this differs

Changing what counts as a change is a contract, not a refactor: `CHANGE_KINDS` in
`packages/core/src/changes.ts` is shared with the control plane and with any SARIF consumer, so
renaming one is a major version.
